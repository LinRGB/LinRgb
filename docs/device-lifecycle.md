## Validation effectuée

Commit logiciel `8b81fee`. Format (`cargo fmt --all -- --check`), Clippy strict (`cargo clippy --all-targets --locked -- -D warnings`), `cargo test --all-targets --locked` : **42 tests**. Les tests couvrent le remplacement de lien HID à modèle identique, le remplacement d'une LED au même chemin avec un writer déjà ouvert, le maintien d'une sélection seulement pour la même instance, et le rejet d'anciennes générations de scans. Les tests de transport utilisent des fichiers temporaires, jamais de commande sur le matériel.

- NixOS : `nix flake check --no-update-lock-file`, construction du paquet, puis `linrgb --diagnostics` sans serveur graphique. Rapport valide, 5 entrées, 1 contrôleur graphique, `active_probing: false`. Les règles udev et leur synchronisation avec le catalogue ont été vérifiées. Pas de `nixos-rebuild switch`.
- Arch `x86_64`, Debian 13 `amd64`, Fedora 44 `x86_64` : dans trois conteneurs, construction du paquet, 42 tests réussis dans chacun, installation et exécution de `linrgb --diagnostics` sous un compte ordinaire. Pas de montage de périphérique RGB dans les conteneurs. Ces essais vérifient compilation, liens dynamiques et lancement sans interface ; pas le bureau ni les ACL d'une vraie session.
- Sources : archive `git archive` du commit local. **Uniquement dans les copies de test**, remplacement de la source épinglée et du checksum par cette archive ; aucun changement de pin publié. Les artefacts de validation portant le numéro `-4` ne sont pas des mises à jour de distribution. Ne pas les publier comme tels.

## Recette physique non destructive (à faire)

1. Quitter les autres programmes RGB et l'ancienne instance de LinRgb. Depuis ce worktree : `nix run . -- --diagnostics`, puis `nix run .`. Utiliser une session locale normale, jamais `sudo`. Ne pas cliquer sur Appliquer pendant la vérification passive.
2. Noter les lignes présentes. Sur un **périphérique USB externe dont le débranchement est prévu par le constructeur**, débrancher, attendre le retrait de la ligne, puis rebrancher au même port. Vérifier l'apparition d'une seule ligne, sans sélection de la nouvelle instance ni modification spontanée de couleur. Ne pas débrancher à chaud un connecteur RGB interne, un DIMM ou une carte PCIe. Un hub interne sera vérifié par démarrage/arrêt normal, pas par débranchement à chaud.
3. Sur un périphérique USB pris en charge par la classe LED multicolore Linux, répéter l'étape 2. Vérifier l'ordre des canaux et le maximum affiché, puis leur présence après reconnexion, **sans** cliquer sur Actualiser. Sans ce matériel, noter « non testé », ne pas créer de LED sur la machine pour simuler le succès.
4. Enregistrer le travail ouvert. Mettre la machine en veille via le bureau, puis reprendre la session. Vérifier que les lignes sont réévaluées, qu'aucun profil n'est appliqué seul et que l'application reste utilisable. En session avec tray, masquer et restaurer la fenêtre ; ne pas confondre fermeture dans le tray et arrêt de l'application.
5. Si un test visuel est souhaité, choisir **un** périphérique déjà validé, noter sa couleur et appliquer une couleur fixe, puis la couleur initiale. Pour un essai d'effet, utiliser un fondu lent et l'arrêter explicitement. Sur une RAM inconnue, ne pas sélectionner l'emplacement pour tester la découverte. Ne pas modifier les permissions ni le firmware. Documenter séparément les résultats physiques et ceux des tests simulés.

## Étape architecturale suivante

Pas de plugins binaires ni d'ABI dynamique pour l'instant. Commencer par un contrat de test pour **deux pilotes existants** : `observe(metadata)` produit un candidat et ses capacités connues ; `open(validated attachment)` retourne un writer limité à cette connexion. Distinguer les capacités lues de celles définies par une fiche expérimentale. Ne factoriser un registre statique qu'après avoir vérifié ces deux implémentations avec des fixtures positives, négatives et de retrait. Pour Aura, collecter d'abord des descripteurs versionnés avant de remplacer les dimensions fixes ou de prendre en charge d'autres cartes. Pour le SMBus et les GPU, la continuité d'identité entre inventaire et ouverture reste un chantier distinct.
